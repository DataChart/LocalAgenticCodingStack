FULLY LOCAL, SELF-HOSTED
CLAUDE CODE EQUIVALENT

Implementation Guide for a Four-GPU Windows 11 Workstation

Component Target
Host Windows 11 with WSL2 / Ubuntu 24.04
Compute 4 x NVIDIA RTX 4070, 12 GB each; no NVLink
CPU / RAM Intel i5-14400F / 32 GB RAM
Storage 2 TB SSD
Primary result Local coding agent, multi-agent orchestration, scheduling, MCP, sandboxing and observability

Prepared October 20, 2026

Version-sensitive technical claims were checked against documentation available on this date. Performance figures remain estimates until measured on the actual motherboard topology.

Executive Decision

Implement the workstation with WSL2 and Ubuntu 24.04. Run two independent local inference services: Qwen3-Coder-30B-A3B-Instruct on GPUs 0-1 as the primary coding model, and gpt-oss-20b on GPUs 2-3 for planning, review, summaries and subagents. Put LiteLLM in front of both services, use OpenCode as the daily terminal harness, and use LangGraph plus Prefect for owned orchestration and scheduled work.

Critical assumption: all four RTX 4070s are visible to CUDA and each slot negotiates at least PCIe 4.0 x4. If any slot runs at x1, avoid splitting a single model across that GPU.

1. Architecture Decision

Recommendation: WSL2, not Windows-native or dual boot

Option Decision Reason
Windows-native No Good desktop integration, but weaker compatibility with Linux-first inference servers, container sandboxes, NVIDIA exporters, MCP servers and orchestration tools.
WSL2 Ubuntu 24.04 Recommended Best compromise: Linux CUDA applications, Docker, namespaces, shell tools and Windows/VS Code integration without rebooting.
Dual-boot Ubuntu Only if WSL benchmarks fail Lowest virtualization and filesystem friction, but poor daily-driver ergonomics because Windows and Linux cannot be used simultaneously.

Filesystem rule

Keep active repositories inside the WSL virtual disk:

/home/caleb/src/project

Do not run agent-heavy repositories from:

/mnt/c/Users/Caleb/source/project

wsl -d Ubuntu-24.04 --cd /home/caleb/src/project code .

Primary deployment topology

  • GPU 0 + GPU 1: Qwen3-Coder-30B-A3B-Instruct, primary coding model.

  • GPU 2 + GPU 3: gpt-oss-20b, planner, reviewer, summarizer and subagent model.

  • CPU: gateway, orchestration, Git, MCP and test coordination.

  • Docker containers: command sandbox, observability, Prefect and optional Langfuse.

  • Windows: VS Code frontend only.

  • WSL: repositories, models, agents, inference servers and containers.

2. Inference Layer

Engine comparison for four 12 GB RTX 4070s

Engine Multi-GPU / quantization Tooling and WSL2 fit Verdict
llama.cpp Layer splitting; broad GGUF Q2-Q8 support Template-dependent tool calls; excellent WSL2 fit Primary choice
vLLM Tensor/pipeline parallelism; AWQ, GPTQ, FP8 and FP8 KV Strong parser framework and continuous batching; good WSL2 fit Second-stage benchmark

Do not default to tensor parallel size 4. With no NVLink, synchronization traverses PCIe. On unknown motherboard lanes, layer splitting or two independent two-GPU servers is safer and often more predictable.

  • PCIe 4.0 x8/x16: good.

Speculative decoding

Do not make speculative decoding part of version 1. Benchmark it later with a tokenizer-compatible small Qwen draft model. It is most useful when the target model is expensive per decoded token, tokenizer compatibility is exact, draft acceptance is high, and PCIe traffic does not erase the gain.

Anthropic Messages compatibility

  • Treat OpenAI-compatible /v1/chat/completions as authoritative.

  • Use Anthropic-format translation only after tool-call regression tests pass.

  • Do not assume Claude prompt caching, extended-thinking fields, computer-use blocks or exact streaming events exist locally.

  • Expect brittleness from clients that hard-code Anthropic-specific content block types.

Pointing CLIs at the gateway

export OPENAI_API_KEY="$LITELLM_MASTER_KEY"
export OPENAI_BASE_URL="http://127.0.0.1:4000/v1"

  • Tool-call delimiters may not match a model template.

  • Clients may send unsupported prompt-caching parameters.

  • Anthropic content blocks may not translate cleanly to OpenAI tool calls.

  • Local KV limits may be overrun by clients assuming 200K context.

  • Harmony or analysis channels may be discarded incorrectly.

  • Parallel tool calls may contain malformed JSON.

Recommended combination

Secret handling and prompt injection

  1. Keep secrets outside repositories.

  2. Pass short-lived credentials through process environment only.

  3. Redact known secret patterns before logging.

  4. Never mount ~/.ssh, Windows profile directories or the Docker socket.

  5. Use separate read-only database identities for agents.

  6. Run gitleaks before commits.

docker run --rm -v "$PWD:/repo" zricethezav/gitleaks:latest detect --source=/repo --no-git

  • Tool permissions are enforced by policy code, not prompt text.

  • Fetched content never becomes a system message.

  • Tool output is length-limited and provenance-tagged.

  • Secrets are unavailable to the tool container.

  • Network access is off by default.

  • Commands use structured argv arrays, not shell=True.

  • Repository instructions cannot override hard policy.

  • External side effects require confirmation.

Model gaps and mitigations

  • Weaker abstraction discovery across very large repositories.

  • Lower reliability over 30-50 tool interactions.

  • More difficulty recovering from misleading tests.

  • Less consistent recognition of conflicting requirements.

  • Tool-call validity degrades under context pressure.

  • Self-review may reinforce an incorrect architecture.

  1. Limit each executor to one narrow objective.

  2. Require tests after each meaningful edit group.

  3. Give reviewers task, diff, relevant files and test output rather than the raw transcript.

  4. Use deterministic patch tools instead of whole-file rewrites.

  5. Re-plan after two consecutive failed test passes.

  6. Cap autonomous steps.

  7. Keep humans in the loop for dependencies, schemas, deployments and Git pushes.

  8. Retrieve relevant files instead of stuffing the entire repository into context.

Hardware bottlenecks and upgrades

  • PCIe topology is the largest unknown. If a slot is x1, use that card for an independent small model rather than cross-GPU splitting.

  • Four 12 GB cards do not behave like one 48 GB card. Per-process allocations must balance and fragmentation can still cause OOM.

  • The i5-14400F is adequate for coordination and light builds, but can bottleneck concurrent test suites and CPU-offloaded models.

  • Upgrade system RAM to 64 GB minimum; 96 or 128 GB is preferred if supported reliably.

  • If model quality remains limiting, replace two 4070s with one 24 GB or 32 GB GPU rather than adding a fifth small card.

Power, heat and noise

Four RTX 4070-class cards can approach roughly 800 W of board power before CPU and system losses. Begin with conservative per-card limits and validate thermals before unattended schedules.

sudo nvidia-smi -pl 160
nvidia-smi --query-gpu=index,power.min_limit,power.max_limit,power.default_limit --format=csv
nvidia-smi --query-gpu=index,temperature.gpu,power.draw,power.limit,utilization.gpu,clocks.sm --format=csv -l 2

  • Use a high-quality PSU sized for simultaneous transient load.

  • Use direct PSU cables rather than overloaded splitters.

  • Provide strong front-to-back airflow and spacing between cards.

  • Add temperature-triggered shutdown behavior.

  • Validate sustained operation before enabling unattended scheduled work.
